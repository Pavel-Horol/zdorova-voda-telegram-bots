# План: UX-улучшения клиентского бота

Три фичи: (1) постоянное reply-меню, (2) «Назад»/«Отмена» в шагах FSM,
(3) явный итог перед подтверждением. Всё — в клиентском боте; диспетчерский,
pricing и схема БД **не затрагиваются** (кроме одного read-only метода в orders).

---

## 0. Что есть сейчас (факты из кода)

- `client-bot.service.ts` — весь FSM: `step` (enum `Step`) + `bottles` в in-memory
  сессии grammY. Навигация — через **inline** callback-кнопки.
- Главное меню = inline-кнопка `CB_ORDER` («🚰 Заказать воду»).
- `onText` обрабатывает текст **только** на шаге `AwaitAddress`.
- Переходы: `onOrder` → (нет адреса → `AwaitAddress`; есть → `ChooseQty`) →
  `onChooseQty` (`orders.quote` + экран Confirm) → `onConfirmYes` (`createOrder`).
- `texts.confirm(quote, address)` уже даёт текст подтверждения, но без
  структурированного итога и без кнопки «Изменить».
- `orders.service` **не имеет** метода списка заказов клиента (нужен для «Мои заказы»).
- `src/config/` **не создан**; `SUPPORT_PHONE` нигде не читается (нужен для «Связаться»).
  `ConfigService` уже доступен (инжектится в бот) — значит `ConfigModule` есть.
- `Address`: `raw` (вся строка адреса), `comment?` (сейчас всегда null), `isDefault`.

## Фича 1. Постоянное reply-меню (4 кнопки)

**Цель:** внизу всегда висят «🚰 Заказать воду», «📋 Мои заказы», «💰 Цены»,
«📞 Связаться». Снимает необходимость помнить команды.

### Изменения
- **`client-bot.service.ts`**
  - Добавить `mainReplyKeyboard = new Keyboard().text('🚰 Заказать воду').row()
    .text('📋 Мои заказы').text('💰 Цены').row().text('📞 Связаться').resized()`
    (persistent, **без** `oneTime`).
  - Заменить отправку `mainMenuKeyboard` (inline) на `mainReplyKeyboard` во всех
    точках возврата в меню: `onStart`, `onContact`, `onConfirmYes`, `onConfirmNo`,
    `requireClient`-фоллбэк. Inline `mainMenuKeyboard` удалить.
  - **Маршрутизация текста (ключевой момент).** Reply-кнопки приходят как
    `message:text`. Ввести в начале `onText` диспетчер по тексту кнопки:
    - «🚰 Заказать воду» → `onOrder`-логика (вынести в общий метод `startOrder`);
    - «📋 Мои заказы» → `showHistory`;
    - «💰 Цены» → `showPrices`;
    - «📞 Связаться» → `showContacts`.
    Эти кнопки работают **глобально** (в т.ч. прерывают `AwaitAddress`): сначала
    проверяем совпадение с кнопкой меню, и только если не совпало и `step ===
    AwaitAddress` — трактуем текст как адрес. Это защищает от сохранения «💰 Цены»
    как адреса.
  - `onOrder` (callback `CB_ORDER`) больше не нужен как точка входа из меню, но
    оставим/переиспользуем общий `startOrder(ctx)`.
- **`client-bot.texts.ts`**
  - `mainMenu(name)` — оставить (текст приветствия над reply-клавой).
  - Добавить `history(orders)`, `prices(p: PriceComponents)`, `contacts(phone)`,
    `historyEmpty`.
- **`orders.service.ts`** — новый read-only метод
  `listByClient(clientId, limit = 5): Promise<Order[]>` (findMany, orderBy
  createdAt desc, take limit). Доступ к БД остаётся внутри сервиса (CLAUDE.md §6).
- **«Цены»** — читаем `pricingSettings.getCurrent()` (метод уже есть) и форматируем.
  Нужно прокинуть `PricingSettingsService` в бот **или** добавить тонкий
  `orders.getPriceInfo()` фасад (предпочтительно — фасад в orders, чтобы бот не
  знал про pricing-settings напрямую; согласуется с тем, что бот уже зависит от
  `OrdersService`).
- **«Связаться»** — читать `SUPPORT_PHONE` через `ConfigService`. Это уже значится
  в `.env`/CLAUDE.md и в SPEC §11 как заглушка перед запуском.

### Влияние / риски
- Фундаментальный сдвиг навигации с inline-меню на reply-клаву + текстовый роутер.
  Это меняет структуру `onText`, но в рамках одного файла.
- Коллизия «текст-кнопка vs ввод адреса» — решается приоритетом кнопок меню.
- Расширяет поверхность MVP двумя экранами («Мои заказы», «Цены»). Оба **входят**
  в §10 («История заказов клиента», «Редактирование цен» → показ цен логично).
  Формально новые экраны — обновить SPEC §6.

## Фича 2. «◀ Назад» / «❌ Отмена» в шагах FSM

**Цель:** на каждом шаге можно вернуться на предыдущий экран или выйти в меню,
не делая `/start`.

### Изменения
- **`SessionData`** — добавить стек истории: `history: Step[]`. При входе на новый
  шаг — `push` предыдущего; «Назад» — `pop` и ре-рендер. Альтернатива (проще, но
  менее гибко) — одно поле `prevStep`. Рекомендую стек: линейный флоу короткий,
  стек тривиален и расширяем.
- **Рефактор экранов в render-хелперы**, чтобы «Назад» мог их переотрисовать:
  `renderChooseQty(ctx)`, `renderConfirm(ctx)`, `renderAddressPrompt(ctx)`. Сейчас
  отрисовка размазана по хендлерам — вынести в приватные методы.
- **Inline-клавиатуры шагов** дополнить кнопками:
  - `ChooseQty`: ряд цифр + ряд `[◀ Назад] [❌ Отмена]`.
  - `Confirm`: см. Фичу 3 (там же «Изменить» = back).
  - `AwaitAddress`: это текстовый ввод — отправлять под приглашением inline
    `[❌ Отмена]` (одна кнопка), т.к. «назад» с первого шага = выход в меню.
- **Новые callback'и** `CB_BACK`, `CB_CANCEL`:
  - `CB_CANCEL` → очистить `bottles`/`history`, `step = MainMenu`, показать меню
    (reply-клава) + текст «Отменено».
  - `CB_BACK` → `pop` истории, `step = popped`, вызвать соответствующий
    `render*`. Если стек пуст → меню.
- **Семантика переходов** (зафиксировать в SPEC §6):
  - Confirm → Назад/Изменить → ChooseQty.
  - ChooseQty → Назад → MainMenu (для повторного) или AwaitAddress (для первого,
    если адрес только что вводили — но обычно сразу в меню; упростим: в меню).

### Влияние / риски
- Главное усложнение — аккуратный ре-рендер. Снимается выносом `render*`-хелперов.
- Нужно следить за идемпотентностью (уже есть проверка `step !== Confirm` в
  `onConfirmYes`) — стек не должен её ломать.
- Только in-memory сессия; при рестарте стек теряется — приемлемо для MVP (SPEC §9).

## Фича 3. Явный итог перед подтверждением

**Цель:** перед финальным «Подтвердить» — структурированная сводка.

### Целевой экран
```
Хочу заказать:
📦 2 бутыли (по 75 грн)
📍 ул. Хмельницкого 2, кв 5 (домофон 45)
💰 К оплате: 150 грн (наличными водителю)

[✅ Всё верно, заказываю]
[✏️ Изменить]  [❌ Отмена]
```

### Изменения
- **`client-bot.texts.ts`** — переписать `confirm(quote, address)` под структуру
  выше. Для первого заказа — ветка с разбивкой залог+помпа (как сейчас), для
  повторного — «N бутылей (по X грн)». Адрес: показываем `address.raw`
  (+`comment` в скобках, если появится). Склонение «бутыль/бутыли/бутылей» —
  маленький хелпер.
- **`confirmKeyboard`** — три кнопки на двух рядах: `CB_CONFIRM_YES`
  («✅ Всё верно, заказываю»), `CB_BACK`/`CB_EDIT` («✏️ Изменить» → ChooseQty),
  `CB_CONFIRM_NO`/`CB_CANCEL` («❌ Отмена»). «Изменить» = back из Фичи 2 (не
  плодить отдельную логику).
- Логика `onConfirmYes`/`onConfirmNo` — без изменений по сути (та же
  `createOrder` / возврат в меню).

### Влияние / риски
- Почти полностью изоляция в `texts.ts` + клавиатура. Самая дешёвая из трёх фич.
- `perBottle` для повторного уже есть в `OrderQuote`; для первого «по X грн»
  заменяем на разбивку — данные в quote есть (`depositPerBottle`, `pumpPrice`).

## Порядок реализации (рекомендуемый)

1. **Фича 1** — фундамент навигации (reply-клава + текстовый роутер + методы
   history/prices/contacts + `orders.listByClient` + чтение `SUPPORT_PHONE`).
2. **Фича 3** — дешёвая, изолированная в текстах/клавиатуре подтверждения.
3. **Фича 2** — стек истории + `render*`-хелперы + Назад/Отмена/Изменить
   (опирается на render-хелперы, которые удобно ввести последними).

## Затрагиваемые файлы (итог)
- `src/bots/client-bot/client-bot.service.ts` — основная работа.
- `src/bots/client-bot/client-bot.texts.ts` — новые/переписанные тексты.
- `src/modules/orders/orders.service.ts` — `listByClient` (+ опц. `getPriceInfo`).
- `SPEC.md` §6 — обновить FSM: reply-меню, экраны «Мои заказы»/«Цены»/«Связаться»,
  Назад/Отмена, новый формат CONFIRM (CLAUDE.md прав. 4 — тем же коммитом).
- (Возможно) `src/config/` или `.env` — задокументировать `SUPPORT_PHONE`.

## Что НЕ трогаем
- Расчёт цены (только pricing.service, CLAUDE.md §1) — бот по-прежнему лишь
  показывает данные из `quote`/`getCurrent`.
- Схема БД — миграции не нужны (`comment` у Address уже есть).
- Диспетчерский бот, OrderDispatcher, статусы заказов.

## Тесты
- Юнит-тест на `orders.listByClient` (порядок/лимит) — необязательно, но дёшево.
- Хелпер склонения «бутыль» — чистая функция, можно покрыть.
- Хендлеры grammY вручную/в dev — автотесты ботов в MVP не вводим.

## Оценка
Реализуемо полностью, без архитектурных конфликтов. Объём — средний: ~1 файл
бота переписывается заметно (роутинг + стек + хелперы), тексты и один метод
сервиса — мелочь. Главный аккуратный момент — приоритет reply-кнопок над вводом
адреса и ре-рендер по «Назад».
