# PRODUCT.md

Продуктовый справочник: **как система работает и почему**. Описывает поведение
и бизнес-правила в настоящем времени — это референс для понимания «почему код
такой», а не план фич. Технические конвенции и команды — в `CLAUDE.md`.

---

## Назначение
Telegram-бот принимает заказы бутилированной воды (бутыли 19 л) и разгружает
телефон диспетчера: постоянные клиенты оформляют повторный заказ в несколько
тапов, новые — оформляют первый заказ, который диспетчер подтверждает звонком.
Бот забирает массовый простой сценарий; редкие и сложные случаи остаются на
диспетчере. С водителями бот не общается — диспетчер вручную пересылает им
строку заказа.

## Действующие лица
- **Клиент** — клиентский бот: оформляет заказ.
- **Диспетчер** — диспетчерский бот: принимает заказы, меняет статусы, правит
  цены, пересылает заказ водителю.
- **Водитель** — вне системы: получает заказ от диспетчера, доставляет, берёт
  оплату на месте.

## Ценообразование

### Повторный заказ (клиент уже в базе бота)
Цена за бутыль зависит от количества:

| Количество | Цена за бутыль |
|-----------|----------------|
| 1 | `price1` (по умолч. 80) |
| 2 | `price2` (по умолч. 75) |
| 3 и больше | `price3plus` (по умолч. 70) |

### Первый заказ (клиента ещё нет в базе)
Вода бесплатно, оплачивается стартовый комплект:
`количество × depositPerBottle (300) + pumpPrice (200)`.
Примеры: 1 → 500, 2 → 800, 3 → 1100. Всегда одна помпа. 2+ помпы и чужие бутыли —
вне автоматики, диспетчер решает при звонке-подтверждении.

### Откуда берутся цифры
Все суммы (`price1/2/3plus`, `depositPerBottle`, `pumpPrice`) хранятся в БД
(`PriceSettings`), **не в коде**, и редактируются диспетчером. Любой расчёт берёт
актуальные значения на момент оформления.

## Расчёт суммы (единое правило — `pricing.service.ts`)
```
calcTotal(bottles, isFirstOrder, prices):
  if isFirstOrder:
    return bottles * prices.depositPerBottle + prices.pumpPrice
  else:
    perBottle = bottles == 1 ? price1 : bottles == 2 ? price2 : price3plus
    return bottles * perBottle
```
**`isFirstOrder`**: у клиента нет ни одного заказа со статусом, отличным от
`cancelled`. `totalPrice` фиксируется в `Order` при создании и задним числом не
пересчитывается — даже если диспетчер потом изменит цены (важно для корректной
истории).

## Модель данных (концептуально; точная схема — `prisma/schema.prisma`)
- **Client** — `id`, `telegramId` (uniq), `phone` (uniq), `name?`, `createdAt`.
- **Address** — `id`, `clientId`, `raw` (как ввёл клиент), `comment?` (этаж/домофон),
  `isDefault`, `createdAt`. В UI показывается только default-адрес; модель
  допускает несколько (лёгкое расширение).
- **Order** — `id`, `clientId`, `addressId`, `bottles`, `isFirstOrder`,
  `totalPrice` (фикс. на момент заказа), `status` (created/accepted/delivered/cancelled),
  `createdAt`, `acceptedAt?`, `deliveredAt?`.
- **PriceSettings** — `price1`, `price2`, `price3plus`, `depositPerBottle`,
  `pumpPrice`, `updatedAt`. Деньги — целые гривны (`int`), без копеек.

## Поведение клиентского бота
**Постоянное reply-меню** (всегда внизу): 🚰 Заказать воду · 📋 Мои заказы ·
💰 Цены · 📞 Связаться.

**Глобальная навигация:** нажатие любой reply-кнопки в любой момент отменяет
текущий FSM (если он не в `MAIN_MENU`), сбрасывает историю переходов и ведёт на
запрошенный экран. Если шёл активный заказ — показывается «Заказ отменён».

**Внутри сценария заказа** (AwaitAddress / AwaitComment / ChooseQty / Confirm)
доступны inline-кнопки «◀ Назад» (на предыдущий шаг по стеку истории) и
«❌ Отмена» (сброс заказа в главное меню).

**Потоки:**
- `/start`: известный клиент → главное меню; новый → запрос контакта (без контакта
  дальше не пускаем).
- «Заказать воду»: первый заказ → AwaitAddress → AwaitComment → ChooseQty →
  Confirm; повторный (есть адрес) → сразу ChooseQty (+ кнопка «Повторить прошлый
  заказ») → Confirm.
- Подтверждение → создаётся `Order(created)` → уведомление диспетчеру →
  «Заказ принят, ожидайте».
- «Мои заказы»: последние заказы; под заказами в статусе `created` — кнопка
  отмены (клиент отменяет сам, пока диспетчер не принял).
- «Цены»: текущая сетка из `PriceSettings`. «Связаться»: `SUPPORT_PHONE` из конфига.

## Поведение диспетчерского бота
Новый заказ приходит карточкой (с пометкой «ПЕРВЫЙ ЗАКАЗ», если так) и кнопками
по статусу:
- «Принят» → `accepted`, кнопки сменяются на [Доставлен] [Изменить] [Отменить];
  клиенту уходит уведомление. Диспетчер вручную пересылает строку заказа водителю.
- «Изменить» (только created/accepted) → ввод нового кол-ва → пересчёт через
  pricing по текущим ценам (осознанный оверрайд зафиксированной суммы).
- «Доставлен» → `delivered`, заказ закрыт. «Отменён» → `cancelled`.

Команды/reply-меню диспетчера: `/orders` (📋 Активные — created/accepted
карточками), `/prices` (💰 — показ и правка цен), `/stats` (📊 — статистика по
данным бота). Строка заказа для пересылки водителю формируется в привычном
диспетчеру формате, напр. `2по75 Хмельницкого 2 кв5 (домофон 45)`, для первого —
с пометкой `[ПЕРВЫЙ +помпа]`.

## Сквозной путь заказа (happy path)
Клиент оформляет → `created` → уведомление диспетчеру → диспетчер «Принят» →
`accepted` + уведомление клиенту, пересылает водителю → водитель доставил →
диспетчер «Доставлен» → `delivered` + уведомление клиенту, оплата у водителя.
Смена статуса диспетчером уведомляет клиента через событие `order.status.changed`;
отмена самим клиентом клиенту повторно не дублируется.

## Edge-кейсы и принятые решения
Это «почему код такой» — самая ценная часть для понимания при доработках.

| Случай | Решение |
|--------|---------|
| Клиент не делится контактом | Не пускаем дальше AwaitContact, объясняем зачем |
| Первый заказ, нужна 2-я помпа / нестандарт | Считаем 1 помпу; диспетчер уточнит звонком |
| Заказ вне зоны / другой город | Принимаем; диспетчер видит адрес и отменяет/звонит |
| Кривой адрес | Принимаем как `raw`; диспетчер уточнит |
| Двойной тап «подтвердить» | Идемпотентность: уводим из Confirm ДО создания заказа |
| Клиент отменяет сам | Только статус `created` и только свой заказ (владелец по `clientId`) |
| Гонка «Отмена» клиента vs «Принят» диспетчера | Атомарный апдейт `where:{status:created}` — кто первый |
| Не-текст на шаге адреса/комментария | Просим прислать текстом, экран не сбрасываем |
| Подделанный callback (кол-во/чужой заказ) | Кол-во ограничено сверху (`MAX_ORDER_QTY`); владелец проверяется по `clientId` |
| Сбой создания заказа (БД) | Сообщаем «не удалось, попробуйте ещё раз», не молчим |
| Цена изменилась после оформления | Не пересчитываем — `totalPrice` зафиксирован |
| Бот перезапустился в середине диалога | Сессия in-memory; при потере клиент начинает заказ заново (приемлемо) |
