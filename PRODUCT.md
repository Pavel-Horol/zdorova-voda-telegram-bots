# PRODUCT.md

Продуктовый справочник: **как система работает и почему**. Описывает поведение
и бизнес-правила в настоящем времени — это референс для понимания «почему код
такой», а не план фич. Технические конвенции и команды — в `CLAUDE.md`.

---

## Назначение
Telegram-бот принимает заказы бутилированной воды (бутыли 19 л) и разгружает
телефон диспетчера: постоянные клиенты оформляют повторный заказ в несколько
тапов, новые — оформляют первый заказ, который диспетчер подтверждает звонком.
Бот забирает массовый простой сценарий; редкие и сложные случаи остаются на
диспетчере. С водителями бот не общается — диспетчер вручную пересылает им
строку заказа.

## Действующие лица
- **Клиент** — клиентский бот: оформляет заказ.
- **Диспетчер** — диспетчерский бот: принимает заказы, меняет статусы, правит
  цены, пересылает заказ водителю.
- **Водитель** — вне системы: получает заказ от диспетчера, доставляет, берёт
  оплату на месте.

## Ценообразование

> Действующие бизнес-правила (прайс с 12.05.2026). Расчёт реализован в
> `pricing.service` (`calculateTotal` по `kind` заказа, включая добор тары). Пока НЕ
> из бота: выбор электро-помпы (T5) и тип OWN_TARA как ветка онбординга (T3) —
> формулы для них готовы, но заказы такого типа ещё не создаются.

**Бот считает только городской тариф** (квартира / дом / офис). Тарифы «киоск/бар»
(60) и «розливайки» (50) — только по телефону, в боте их нет.

### Повторный заказ (тара клиента уже в обороте)
Цена за бутыль воды зависит от количества — пороги **1 / от 2 / от 6**:

| Количество | Цена за бутыль |
|-----------|----------------|
| 1 | `price1` (80) |
| 2–5 | `priceFrom2` (70) |
| 6 и больше | `priceFrom6` (65) |

Отдельной цены за «ровно 2» нет: 2 бутыли = `2 × priceFrom2 = 140`.

### Первый заказ — стартовый комплект (бандл с фиксированной ценой)
Новичок покупает комплект «бак(и) + помпа + вода» по **фиксированной цене бандла**,
а НЕ как сумму компонентов:

Комплект **раскладывается на компоненты** (не хранится отдельной ценой):
`bottles × depositPerBottle + pumpPrice + bottles × waterStartPrice`.

| Комплект | Состав | Цена |
|---|---|---|
| 1 бак | 450 + 250 + 50 | `750` |
| 2 бака | 2×450 + 250 + 2×50 | `1250` |
| n баков | n×450 + 250 + n×50 | `n×500 + 250` |

В комплекте **всегда 1 помпа**. Электро-помпа — замена обычной: `electroPumpPrice`
(270) вместо `pumpPrice` (250), т.е. комплект +20 (старт1 электро = 770). Старт-вода
(`waterStartPrice` 50/бак) — включённая в комплект первая партия (НЕ «бесплатная вода»).

### Компоненты (поштучно, вне комплекта)
Применяются при доборе тары, докупке помпы, чужой таре:
- залог за бак: `depositPerBottle` (450)
- помпа: `pumpPrice` (250), электро: `electroPumpPrice` (270)

### Свои баки (включая чужой бренд)
У клиента уже есть баки 19 л → за **обмениваемые** баки платит только воду по сетке,
**залог 0**. Не важно, наши это баки или другого бренда: чужие баки мы принимаем,
переклеиваем этикетку, и они становятся нашими (поликарбонат, проходят по качеству;
качество проверяет водитель при доставке). Поэтому **отдельного «чужого» состояния
нет** — все «есть баки» считаются как OWN_TARA. Заявленное количество баков диспетчер
сверяет физически при приёме (см. «отложенный коммит баланса»).

**Добор тары на OWN_TARA — как на повторном.** Если заказано больше баков, чем у
клиента на руках (заявленный `claimedOnHand`), то за каждый бак сверх остатка берётся
залог, вода по сетке — на всё количество. Формула совпадает с REPEAT: разница лишь в
источнике остатка (заявление клиента против оборота из доставок). Пример: на руках 3,
заказал 4 → `4×70 + 450 = 730`. Раньше OWN_TARA ошибочно считалась «всегда обмен,
залог 0» при любом количестве — 4-й бак уезжал без залога.

### Добор тары на повторном
Заказ больше баков, чем на руках → за каждый новый бак берётся залог; вода по сетке
считается на **всё количество** (по тарифу за общее число бутылей, как обычно):
`вода по сетке × всё количество + 450 × (заказано − на руках)`.
Пример: на руках 1, заказал 2 → `2×70 + 450 = 590`.

Баланс тары (`Client.bottlesOnHand`) начисляется **при доставке** заказа: STARTER_KIT —
все баки, добор — новые баки сверх остатка. На нём и считается добор у повторного.

### Откуда берутся цифры
Все суммы хранятся в БД (`PriceSettings`), **не в коде**, и редактируются
диспетчером. Любой расчёт берёт актуальные значения на момент оформления.

## Расчёт суммы (единое правило — `pricing.service.ts`)
```
calcTotal(bottles, kind, prices):
  STARTER_KIT(electro?):                    # первый заказ: бак(и) + помпа + старт-вода
    pump = electro ? prices.electroPumpPrice : prices.pumpPrice
    return bottles*prices.depositPerBottle + pump + bottles*prices.waterStartPrice
  OWN_TARA:                                 # своя тара, помпа есть → залог 0
    return waterByGrid(bottles, prices)
  REPEAT(bottlesOnHand):                    # тара в обороте
    newTara = max(0, bottles - bottlesOnHand)   # баки сверх остатка → залог
    return waterByGrid(bottles, prices) + newTara * prices.depositPerBottle

waterByGrid(n, p) = n * (n == 1 ? p.price1 : n < 6 ? p.priceFrom2 : p.priceFrom6)
```
> `kind` приходит из входного состояния клиента (см. «Решено, не реализовано»),
> заменяя прежний `isFirstOrder: boolean`. Текущий код ещё на `isFirstOrder`.

`totalPrice` фиксируется в `Order` при создании и задним числом не пересчитывается —
даже если диспетчер потом изменит цены (важно для корректной истории).

## Модель данных (концептуально; точная схема — `prisma/schema.prisma`)
- **Client** — `id`, `telegramId` (uniq), `phone` (uniq), `name?`, `createdAt`,
  `bottlesOnHand` (баков в обороте, дефолт 0), `hasPump` (дефолт false).
- **Address** — `id`, `clientId`, `raw` (как ввёл клиент), `comment?` (этаж/домофон),
  `isDefault`, `createdAt`. В UI показывается только default-адрес; модель
  допускает несколько (лёгкое расширение).
- **Order** — `id`, `clientId`, `addressId`, `bottles`, `kind`
  (STARTER_KIT/OWN_TARA/REPEAT), `totalPrice` (фикс. на момент заказа), `status`
  (created/accepted/delivered/cancelled), `createdAt`, `acceptedAt?`, `deliveredAt?`.
  - `note?` — **комментарий клиента к этому заказу** (напр. «меня не будет с 14 до
    16»). Отличается от `Address.comment` (постоянная подсказка про точку —
    домофон/этаж, переиспользуется между заказами). Виден диспетчеру на карточке и в
    строке водителю.
  - `deliveryNote?` — **последнее сообщение диспетчера клиенту о сроках** («сьогодні»,
    «перенесено на завтра», «протягом години»). Обновляемое; каждое изменение пушит
    клиента и эхом показывается на карточке диспетчера. Не влияет на цену/статус.
- **ContactPhone** — `id`, `phone` (uniq, нормализован к `+<цифры>`), `active`
  (дефолт true), `createdAt`. Телефоны поддержки, которые видит клиент на «Связаться».
  Управляет диспетчер (`/contacts`); клиент видит только `active`. Не синглтон —
  список; при пустом/без активных клиенту показывается резервный `SUPPORT_PHONE`.
- **PriceSettings** — синглтон с ценами. Деньги — целые гривны (`int`), без копеек.
  Целевой набор полей: `price1` (80), `priceFrom2` (70), `priceFrom6` (65),
  `depositPerBottle` (450), `pumpPrice` (250), `electroPumpPrice` (270),
  `waterStartPrice` (50), `updatedAt`. Комплект отдельным полем НЕ хранится —
  считается из залога + помпы + старт-воды. *Текущая схема ещё на старом наборе
  (`price2`/`price3plus` = 75/70, залог 300, помпа 200, без электро и старт-воды) —
  приводится в соответствие рефакторингом.*

## Поведение клиентского бота
**Постоянное reply-меню** (всегда внизу): 🚰 Заказать воду · 📋 Мои заказы ·
💰 Цены · 📞 Связаться.

**Глобальная навигация:** нажатие любой reply-кнопки в любой момент отменяет
текущий FSM (если он не в `MAIN_MENU`), сбрасывает историю переходов и ведёт на
запрошенный экран. Если шёл активный заказ — показывается «Заказ отменён».

**Внутри сценария заказа** (AwaitAddress / AwaitComment / ChooseQty / Confirm)
доступны inline-кнопки «◀ Назад» (на предыдущий шаг по стеку истории) и
«❌ Отмена» (сброс заказа в главное меню).

**Потоки:**
- `/start`: известный клиент → главное меню; новый → запрос контакта (без контакта
  дальше не пускаем).
- **Онбординг** (сразу после регистрации нового клиента, экран «что у вас уже есть»).
  Состояний ровно **два** (см. «Ценообразование»), поэтому три пункта:
  🆕 Стартовый комплект → выбор помпы (обычная 250 / электро 270) → первый-заказ флоу;
  💧 У меня уже есть баки (19 л) → ввод числа баков → «помпа есть?» (нет → докупка 250)
  → заказ OWN_TARA. Ветки «свои баки» и «я уже клиент» **объединены**: и наши баки, и
  чужой бренд (переклеиваем) считаются одинаково (залог 0), а проверку выполняет
  диспетчер при приёме. ⚙️ Другое («попросить диспетчера перезвонить») → уведомление в
  чат диспетчера с просьбой перезвонить + клиенту показываем телефон. Онбординг
  прерван без заказа — покажется снова.
- **Отложенный коммит баланса (верификация).** Заявленное на онбординге число баков
  НЕ пишется в клиента сразу — оно живёт в сессии и фиксируется на заказе
  (`Order.claimedOnHand`); тип заказа становится OWN_TARA. В `Client.bottlesOnHand`
  баланс попадает **только когда диспетчер примет заказ** (приём = верификация). При
  создании OWN_TARA-заказа клиенту ставится `pendingReview`, снимаемый приёмом. Так
  брошенная/отменённая заявка не оставляет в клиенте неподтверждённый баланс (раньше
  оставляла, и онбординг больше не показывался). Цену на Confirm клиент видит из
  заявленного числа — приём фиксирует баланс, физически количество диспетчер сверяет.
- **Помпа на OWN_TARA.** «Помпа есть» → `hasPump` ставится при приёме заказа. «Нужна
  помпа» (`pumpAddon`, +250) → `hasPump` ставится при доставке (как помпа стартового
  комплекта). При вводе числа баков `hasPump` больше автоматически не выставляется.
- **Адрес доставки.** Клиент вводит адрес **текстом** (улица/дом/кв) на шаге AwaitAddress,
  детали входа (этаж/домофон/ориентир) — на шаге `comment` (один шаг, структуру намеренно
  не дробим). Координаты клиент НЕ задаёт — гео-метка только на стороне диспетчера (см.
  «Поведение диспетчерского бота»), который пишет `Address.lat/lng` под будущие маршруты.
- «Заказать воду»: новичок → онбординг; первый заказ (нет адреса) → AwaitAddress →
  AwaitComment → ChooseQty → Confirm; повторный (есть адрес и прошлый заказ) →
  **сразу Confirm с прошлым количеством** [✅ Подтвердить] [✏️ Изменить] [❌ Отмена],
  «Изменить» → ChooseQty; адрес есть, но заказов ещё не было → ChooseQty.
- На экране Confirm — необязательная кнопка «➕ Коментар до замовлення»: клиент может
  добавить заметку к этому заказу (напр. «меня не будет с 14 до 16»), пишется в
  `Order.note`. Возвращает на Confirm; можно очистить. Отдельно от постоянного
  комментария адреса (домофон/этаж), который живёт на `Address`.
- Подтверждение → создаётся `Order(created)` → уведомление диспетчеру →
  «Заказ принят, ожидайте».
- «Мои заказы»: последние заказы; под заказами в статусе `created` — кнопка
  отмены (клиент отменяет сам, пока диспетчер не принял).
- «Цены»: текущая сетка из `PriceSettings`. «Связаться»: **активные** номера из
  `ContactPhone` (управляет диспетчер), по одному на строку; если активных нет —
  показывается резервный `SUPPORT_PHONE` из конфига (он обязателен, см. ниже), так
  что экран никогда не тупик. Ветка онбординга «Інше» берёт первый из тех же номеров.
- «📍 Моя адреса»: показывает сохранённый адрес доставки; кнопка «✏️ Змінити адресу» →
  ввод нового адреса текстом → сохраняет и возвращает в меню. Так клиент меняет адрес вне
  оформления заказа. (Смена текста адреса сбрасывает диспетчерскую гео-метку — она
  указывала на старое место.)

## Поведение диспетчерского бота
Новый заказ приходит карточкой с пометкой по типу: «ПЕРШЕ ЗАМОВЛЕННЯ» (комплект) или
«СВОЯ ТАРА — звірити N баків» (OWN_TARA, N = заявленное `claimedOnHand`). Прежние две
пометки OWN_TARA («проверить бак» и «заявлен действующим») объединены в одну. Кнопки
по статусу:
- «Принят» → `accepted`, кнопки сменяются на [Доставлен] [Изменить] [Отменить];
  клиенту уходит уведомление. Диспетчер вручную пересылает строку заказа водителю.
  Приём OWN_TARA-заказа = верификация: фиксирует `bottlesOnHand = claimedOnHand`,
  снимает `pendingReview`, ставит `hasPump` (если помпа своя).
- «🔢 Звірити баки» (только OWN_TARA в статусе `created`) → ввод реального числа баков →
  правит `Order.claimedOnHand`. Сумму заказа **не меняет** (для OWN_TARA цена = вода по
  сетке + опц. помпа, залог 0, от числа баков не зависит) — это коррекция баланса,
  который коммитится в клиента при приёме, чтобы завышенная заявка не утекла в добор
  тары будущих заказов. После приёма (баланс уже закоммичен) правка недоступна.
- «📋 Рядок водію» (created/accepted) → присылает **отдельным сообщением** компактный
  блок для пересылки водителю (отдельное сообщение → его можно Forward; строка в
  карточке так не пересылается). Формат: `Nпо{ціна/бут} = {сума} грн` (+ `+K бак`, если
  добор тары под залог; + `+помпа` для докупки на OWN_TARA); стартовый комплект —
  `[ПЕРШИЙ N +помпа|+електро] = {сума} грн`. Дальше адрес (+коммент), имя клиента и
  гео-ссылка, если точка задана. Цена/бутыль — из **текущих** цен (информативно), сумма —
  замороженный `totalPrice` заказа.
- «📍 Прив'язати точку» (created/accepted) → координаты доставки на адрес заказа
  (`Address.lat/lng`), под будущую оптимизацию маршрутов. Клиент вводит адрес текстом
  (минимум трения); координаты при надобности проставляет диспетчер, который знает
  адреса. Два способа ввода: **локация Telegram** (мобайл — нативный пин) или
  **вставка** «49.42, 26.99» / ссылки на карту (десктоп). Локация принимается только
  пока активен режим привязки (иначе случайный пин в чате игнорируется). В карточке —
  кликабельная гео-ссылка, если точка задана. Гео-метку ставит только диспетчер; клиент
  координаты не задаёт.
- «✏️ Змінити» (только created/accepted) → под-меню выбора поля: **кол-во**
  (пересчёт через pricing по текущим ценам — осознанный оверрайд зафиксированной
  суммы), **адрес** (текст `Address.raw`) или **комментарий адреса**
  (`Address.comment`). Любая правка содержимого пушит клиента (событие `order.edited`).
- «🕒 Час доставки» (created/accepted) → сообщить клиенту ориентировочное время:
  быстрые пресеты (сьогодні / завтра / протягом години / протягом 2 годин) или «✏️ Свій
  варіант» текстом. Пишет `Order.deliveryNote` (последнее сообщение), пушит клиента и
  эхом показывается на карточке. Обновляемо — покрывает и перенос «на завтра» после
  приёма. Сразу после «Принят» диспетчеру дополнительно предлагается этот выбор
  (можно проигнорировать).
- «Доставлен» → `delivered`, заказ закрыт. «Отменён» → `cancelled`.

Команды/reply-меню диспетчера: `/orders` (📋 Активные — created/accepted
карточками), `/prices` (💰 — показ и правка цен), `/stats` (📊 — статистика по
данным бота), `/client` (🔎 — поиск клиента по телефону: по фрагменту номера →
карточка(и) с балансом тары/помпой, адресом+гео и последним заказом; помогает, когда
клиент звонит), `/contacts` (📞 — телефоны поддержки, которые видит клиент на
«Связаться»: список с пометкой ✅ показывается / 🙈 скрыт; кнопки добавить номер,
скрыть/показать (мягко, номер остаётся) и удалить. Активные номера отдаются клиенту;
если активных нет — клиент видит резервный `SUPPORT_PHONE`. Ввод номера — свободный
текст, нормализуется к `+<цифры>` (`0XX…`→`+380XX…`)). Строка заказа для пересылки водителю — по кнопке «📋 Рядок водію»
(см. выше), напр. `2по70 = 280 грн / Хмельницкого 2 кв5 (домофон 45) / 👤 Іван`, для
первого — `[ПЕРШИЙ N +помпа]`.

## Сквозной путь заказа (happy path)
Клиент оформляет → `created` → уведомление диспетчеру → диспетчер «Принят» →
`accepted` + уведомление клиенту, пересылает водителю → водитель доставил →
диспетчер «Доставлен» → `delivered` + уведомление клиенту, оплата у водителя.
Смена статуса диспетчером уведомляет клиента через событие `order.status.changed`;
отмена самим клиентом клиенту повторно не дублируется.

## Edge-кейсы и принятые решения
Это «почему код такой» — самая ценная часть для понимания при доработках.

| Случай | Решение |
|--------|---------|
| Клиент не делится контактом | Не пускаем дальше AwaitContact, объясняем зачем |
| Первый заказ, нужна 2-я помпа / нестандарт | Считаем 1 помпу; диспетчер уточнит звонком |
| Заказ вне зоны / другой город | Принимаем; диспетчер видит адрес и отменяет/звонит |
| Кривой адрес | Принимаем как `raw`; диспетчер уточнит |
| Двойной тап «подтвердить» | Идемпотентность: уводим из Confirm ДО создания заказа |
| Клиент отменяет сам | Только статус `created` и только свой заказ (владелец по `clientId`) |
| Гонка «Отмена» клиента vs «Принят» диспетчера | Атомарный апдейт `where:{status:created}` — кто первый |
| Не-текст на шаге адреса/комментария | Просим прислать текстом, экран не сбрасываем |
| Подделанный callback (кол-во/чужой заказ) | Кол-во ограничено сверху (`MAX_ORDER_QTY`); владелец проверяется по `clientId` |
| Сбой создания заказа (БД) | Сообщаем «не удалось, попробуйте ещё раз», не молчим |
| Цена изменилась после оформления | Не пересчитываем — `totalPrice` зафиксирован |
| Бот перезапустился в середине диалога | Сессия in-memory; при потере клиент начинает заказ заново (приемлемо) |
