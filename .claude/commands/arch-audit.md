Оцени текущее состояние архитектуры всего проекта по правилам CLAUDE.md.

Это аудит ВСЕГО `src/` (не diff, не PR) — снимок здоровья архитектуры. Гибрид:
сначала детерминированный скрипт, потом твоё рассуждение над «судительными»
правилами, которые grep'ом не берутся. Не чини ничего сам — только отчёт.

## 1. Детерминированная часть
Запусти `node scripts/arch-check.mjs` и включи его вывод в отчёт. Он покрывает:
БД-в-ботах (правило 4), чистоту FSM, импорты Prisma, покрытие чистой логики,
ценовые поля вне pricing.service (правило 1), прямой `ctx.reply` (правило 6),
дрейф схемы. 🔴 — нарушение, 🟡 — кандидат на ручную проверку.

Для каждого 🟡 — посмотри код и вынеси вердикт (нарушение / ок и почему). Напр.
`ctx.reply` внутри `replyInline`/`replyMenu` — это сами обёртки, ок; `ctx.reply`
с разовым текстом (`sendAsText`) — ок; `ctx.reply` с клавиатурой экрана сценария
вне обёрток — нарушение.

## 2. Судительные правила (читай код, рассуждай)
Прочитай: `src/bots/client-bot/*`, `src/bots/dispatcher-bot/*`,
`src/modules/orders/*`, `src/modules/pricing/*`, `src/bots/shared/*`. Проверь:

- **Правило 7 — недоверенный ввод.** Каждый `callbackQuery`-хендлер не доверяет
  `callback_data`/тексту: границы чисел (`MAX_ORDER_QTY`), владелец сущности по
  `clientId` для действий над заказом (как `cancelOwnOrder`). Найди хендлеры, где
  callback используется без проверки границ/владельца.
- **Правило 9 — идемпотентность re-entrant шагов.** Повторный вход не плодит
  дубли: увод из Confirm ДО `createOrder`; upsert/update вместо повторного create
  (default-адрес). Проверь `onConfirmYes`, `setDefaultAddress`, шаги онбординга.
- **Правило 3 — `totalPrice` не пересчитывается** задним числом при смене цен.
  Единственный осознанный пересчёт — `editQuantity`. Убедись, что правка цен
  (`pricing-settings`) не трогает существующие заказы.
- **Правила 2 и 10 — абстракция и событие.** `orders.service` шлёт заказ через
  `OrderDispatcher` (не хардкодит бота) и уведомляет о смене статуса событием
  `order.status.changed`, а не прямым вызовом бота. Проверь импорты `orders.service`
  (не должно быть grammY/конкретного бота).
- **Правило 5 — два бота не смешаны.** Нет общих хендлеров и перекрёстных импортов
  между `client-bot` и `dispatcher-bot`.
- **Правило 8 — сбой даёт обратную связь.** Операции, способные упасть (создание
  заказа, БД), обёрнуты в try/catch в хендлере с понятным сообщением клиенту.
- **FSM проведён полностью.** На каждый `Step` есть гард (`if (ctx.session.step
  !== Step.X) return`) в его хендлере; шаги сценария входят в `ORDER_FLOW_STEPS`;
  поля сессии чистятся в `resetSession`. (Исчерпывающий `renderScreen` гарантирует
  компилятор — отдельно не проверяй.)

## 3. Отчёт
Сгруппируй по правилам. Для каждой находки: severity (🔴 нарушение-баг /
🟡 дрейф-конвенция / ✅ чисто), `файл:строка`, в чём суть, короткий фикс. В конце —
итог: сколько 🔴/🟡, и вердикт «архитектура здорова / есть нарушения». Если всё
чисто — так и скажи, не выдумывай находки ради списка.
