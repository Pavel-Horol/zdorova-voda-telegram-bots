Добавь новый шаг в FSM клиентского бота: $ARGUMENTS

FSM здесь **декларативный**: экраны описаны юнионом `ScreenIntent`, переходы —
чистыми функциями в `src/bots/client-bot/client-bot.fsm.ts`, а превращение интента
в реальный экран — единым исчерпывающим `renderScreen` в сервисе. Состояние шага —
in-memory session grammY (НЕ scenes, НЕ conversations plugin). Главное преимущество:
**забытый экран ловит компилятор** через `assertNever` в `default`-ветке рендера —
не нужно держать в голове список ручных точек.

Перед началом прочитай `CLAUDE.md` (секция «Как устроен FSM») и `PRODUCT.md`
(поведение клиентского бота), чтобы понять, куда шаг встраивается в сценарий.

Процесс (по порядку):

**а) `ScreenIntent` в `client-bot.fsm.ts`** — добавь вариант экрана:
   `| { kind: 'твой-экран'; ...данные для рендера, если есть }`. Клади сюда только
   данные, известные из РЕШЕНИЯ (напр. `bottles`); async-данные (превью цены,
   repeatN, объект адреса) НЕ клади — их грузит хендлер при рендере.

**б) Функция-переход в `client-bot.fsm.ts` + тест** — чистая функция, которая
   решает, КУДА вести: на вход `step`/валидированный ввод/УЖЕ загруженные данные
   (`hasDefaultAddress: boolean`, `bottles: number` — не сервисы, не `ctx`, не
   async), на выход — `ScreenIntent` (сузь возврат через `Extract<ScreenIntent, …>`,
   если вариантов немного). Покрой юнит-тестом в `client-bot.fsm.spec.ts` (по
   образцу `resolveAfterQty`/`resolveConfirm`). Если шаг — это ветка существующего
   перехода, обнови соответствующую функцию, а не плоди новую.

**в) Обработай экран в `renderScreen`** (`client-bot.service.ts`) — добавь
   `case 'твой-экран':` в исчерпывающий switch. **Компилятор сам подскажет**: без
   этого `case` `assertNever(intent)` в `default` перестанет компилироваться
   (`TS2345: … is not assignable to parameter of type 'never'`). Рендер — ТОЛЬКО
   через `replyInline` (inline-сценарий) или `replyMenu` (reply-меню), ставит
   `ctx.session.step = Step.X`. НИКОГДА не `ctx.reply` напрямую (мёртвые кнопки).

**г) Текст в `client-bot.texts.ts`** — добавь сюда, не хардкодь строки в сервисе.

**д) Поле в `SessionData` (`client-bot.service.ts`), ЕСЛИ шаг хранит данные**
   между переходами (по образцу `bottles?`, `addressRaw?`). Снабди комментарием:
   когда живёт, когда чистится. Если добавил поле — очисти его в `resetSession`.

Сопутствующее (только если применимо к шагу):

- **`enum Step`** (`client-bot.fsm.ts`) — новое состояние, если шаг — отдельный
  экран сценария с гардом/историей.
- **`ORDER_FLOW_STEPS`** — добавь шаг, если он внутри сценария заказа (на нём
  работают reply-выход «Заказ отменён» и inline «Назад»/«Отмена»).
- **Гард** в хендлере действия: `if (ctx.session.step !== Step.X) return;`.
- **`pushHistory(ctx, Step.X)`** на входе в шаг, если на него можно вернуться «Назад».
- **callback-кнопки + регистрация** в `registerHandlers` (по образцу `CB_*` и
  `bot.callbackQuery(...)`), если шаг вводит новые кнопки.

После реализации:
- если поведение влияет на продукт — обнови `PRODUCT.md` тем же изменением;
- `npm run lint && npm test` (характеризационные/юнит-тесты переходов должны быть
  зелёными — поведение существующих экранов не ломаем);
- кратко перечисли, какие шаги (а–д + сопутствующее) ты тронул и почему остальные
  не понадобились.

НЕ добавляй scenes/conversations plugin. НЕ заменяй ручное гашение клавиатур.
НЕ возвращай ветвление «какой экран» в хендлеры — решение живёт в fsm.ts, рендер в
`renderScreen`.
