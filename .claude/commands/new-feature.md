Реализуй фичу: $ARGUMENTS

Подход — бизнес-логика в сервисе модуля, покрытая тестами ПЕРВОЙ (как pricing).
Боты остаются тонкими: вызывают сервис, рендерят результат.

Перед началом:
1. Прочитай `PRODUCT.md` — затрагивает ли фича существующие правила (цены,
   isFirstOrder, статусы, edge-кейсы). Если фича МЕНЯЕТ продуктовое правило —
   сначала скажи об этом и обнови `PRODUCT.md` тем же изменением.
2. Прочитай `CLAUDE.md` — архитектурные правила (доступ к БД только в сервисах,
   расчёт сумм только в pricing, OrderDispatcher как абстракция доставки).
3. Если фича выходит за рамки задачи или тянет в «не входит (v2+)» из CLAUDE.md —
   остановись и спроси, прежде чем расширять объём.

Порядок реализации:
1. **Сервисный слой.** Размести логику в нужном `src/modules/<name>/`. Доступ к
   БД — только здесь, через сервис; PrismaClient напрямую из ботов не дёргать.
2. **Тесты ПЕРВОЙ.** Напиши `*.spec.ts` на бизнес-правила (граничные случаи,
   как в pricing.spec). Мокай зависимости, не ходи в реальную БД в юните.
3. **Чистая логика — отдельно.** Любые переходы/парсинг/валидацию, которые
   попадают в бот, выноси в чистые функции (данные грузит хендлер, в функцию
   передаются готовые значения) и покрывай юнит-тестами без живого grammY.
4. **Интеграция в бот** — тонкий хендлер: вызвал сервис → отрендерил через
   `replyInline`/`replyMenu`. Уведомления о смене статуса — через событие
   `order.status.changed`, не прямым вызовом.
5. **Деньги** — только через `pricing.service`. Нигде больше суммы не считать.

Завершение: `npm run lint && npm test`. Сводка — что добавил, какие правила
`PRODUCT.md`/`CLAUDE.md` затронуты.
