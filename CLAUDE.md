# CLAUDE.md

Инструкции для AI-агента (Claude Code) по работе в этом проекте.
Продуктовая логика — в `SPEC.md`. Этот файл — про **как** разрабатывать.

---

## Что это за проект
Telegram-бот приёма заказов воды. Два бота (клиентский + диспетчерский) в одной
кодовой базе NestJS, одна БД. Подробности продукта — всегда сверяйся со `SPEC.md`.

## Стек
- **Node.js** + **TypeScript** (strict)
- **NestJS** — приложение
- **PostgreSQL** + **Prisma** — БД и ORM
- **grammY** — Telegram-боты (два инстанса: client / dispatcher)
- Без Redis в MVP (состояние диалога — в сессии grammY in-memory; при масштабе добавим)

## Структура (целевая)
```
src/
  app.module.ts
  prisma/
    prisma.service.ts        # тонкий сервис-обёртка над PrismaClient
    schema.prisma            # схема (см. модель данных в SPEC.md §4)
  config/                    # env-конфиг (токены ботов, chat_id диспетчера, db url)
  modules/
    clients/                 # клиенты + адреса (сервис, репозиторий)
    orders/                  # заказы: создание, статусы, расчёт цены
      pricing.service.ts     # ЕДИНСТВЕННОЕ место расчёта суммы (SPEC §5)
    pricing-settings/        # чтение/редактирование цен (PriceSettings)
    stats/                   # статистика для диспетчера
  bots/
    client-bot/              # grammY-инстанс №1: диалог клиента (SPEC §6)
      client-bot.service.ts
      scenes/                # шаги FSM: контакт, адрес, выбор кол-ва, подтверждение
    dispatcher-bot/          # grammY-инстанс №2: диалог диспетчера (SPEC §7)
      dispatcher-bot.service.ts
    shared/
      order-dispatcher.ts    # абстракция "куда уходит готовый заказ"
                             # MVP-реализация: шлёт в диспетчерский бот.
                             # v2: добавить ViberDispatcher, не трогая orders.
  common/                    # фильтры, пайпы, утилиты
```

## Ключевые архитектурные правила
1. **Расчёт цены — только в `pricing.service.ts`.** Нигде больше не считать суммы.
   Боты и обработчики вызывают этот сервис. Это единственный источник правды по §5.
2. **`OrderDispatcher` — абстракция доставки заказа.** Бизнес-логика заказа НЕ знает,
   куда уходит уведомление (диспетчер сейчас, Viber потом). Один интерфейс, разные
   реализации. Это закладка под будущую миграцию на прямой Viber (SPEC §10).
3. **`totalPrice` фиксируется в Order при создании.** Не пересчитывать задним числом
   при изменении цен. Цены из `PriceSettings` берутся в момент оформления.
4. **`isFirstOrder` определяется по наличию не-cancelled заказов у клиента** (SPEC §5).
5. **Два бота — два токена, один процесс.** Логику клиента и диспетчера НЕ смешивать
   в общих обработчиках. Разделение по боту, а не по if-ам с проверкой роли.
6. **Доступ к БД — только внутри сервисов модулей.** Боты и хендлеры НИКОГДА не
   дёргают PrismaClient напрямую — только через сервис соответствующего модуля.
   Отдельный репозиторный слой — опционально, когда оркестрация в сервисе
   становится сложной; для простого CRUD достаточно самого сервиса модуля.

## Конвенции кода
- Strict TypeScript, без `any` (если очень надо — комментарий с причиной).
- DTO для входных данных, валидация через `class-validator` где уместно.
- Имена: camelCase для переменных/функций, PascalCase для классов/типов.
- Бизнес-правила, влияющие на продукт, отражать и в `SPEC.md` (не расходиться).
- Деньги — целые числа гривен (`int`), без копеек в MVP.

## Порядок работы над задачами
1. Сверься со `SPEC.md` — какой раздел реализуешь.
2. Сначала схема БД (Prisma), затем сервисы (pricing, orders, clients), затем боты.
3. `pricing.service` и его тесты — в первую очередь: это ядро бизнес-логики, легко
   покрыть юнит-тестами (примеры сумм есть в SPEC §3).
4. Изменил продуктовое правило — обнови `SPEC.md` тем же коммитом.
5. Не расширяй объём за рамки §10 «Границы MVP» без явного решения. Если по ходу
   возникает «а давай ещё фичу» — сначала спроси, относится ли это к MVP.

## Чего НЕ делать
- Не интегрировать Viber API в MVP (диспетчер копирует вручную).
- Не пытаться парсить старую базу адресов — адреса собираются заново через бота.
- Не добавлять онлайн-оплату — оплата всегда у водителя.
- Не городить веб-админку — её роль выполняет диспетчерский бот.
- Не автоматизировать распределение по водителям — это решает диспетчер.
