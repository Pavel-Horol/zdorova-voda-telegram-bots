# CLAUDE.md

Инструкции для AI-агента (Claude Code) по работе в этом проекте.
Описывает **репозиторий как он есть сейчас** и **как в нём работать**.
Продуктовые правила (формулы цен, edge-кейсы, поведение) — в `PRODUCT.md`. UX и правила общения с клиентом (принципы, антипаттерны, микрокопи) — в `UX.md`
(обоснование и ресёрч — в `RESEARCH-UX.md`). Демо-стенд для показа продукта покупателям
(что меняет `DEMO_MODE`, как поднять) — в `DEMO.md`.

---

## Что это
Telegram-бот приёма заказов воды (бутыли 19 л). Два бота в одном NestJS-процессе:
**клиентский** (оформление заказа) и **диспетчерский** (приём заказов, статусы,
цены, статистика). Одна БД. MVP реализован и работает — это не стройка с нуля,
а развитие живого кода. Продуктовый контекст — в `PRODUCT.md`.

## Стек (фактические версии)
- **NestJS 11** + **TypeScript 5.7** (strict)
- **grammY 1.43** — два бота на двух токенах (client / dispatcher), **long polling**
- **Prisma 7.8** через адаптер **`@prisma/adapter-pg`** + **PostgreSQL 16**
- **@nestjs/event-emitter 3** — внутрипроцессная шина (уведомления клиента о смене
  статуса идут событием `order.status.changed`, не прямым вызовом)
- **Jest 30** + ts-jest
- Без Redis (сессия диалога — in-memory в grammY; при масштабе — добавить Redis)

## ⚠️ Prisma 7 — читать перед любой работой со схемой/типами
- Клиент генерится **НЕ в `node_modules`**, а в **`generated/prisma/`**.
- Импорт типов и enum'ов — оттуда: `from '../../../generated/prisma/client'`,
  `from '../../../generated/prisma/enums'`. Считай глубину `../` от своего файла.
- Адаптер `@prisma/adapter-pg` — **не заменять** на дефолтный PrismaClient.
- После любой правки `schema.prisma` — **обязательно** `npm run prisma:generate`,
  иначе типы разъедутся с БД.
- `BigInt` для `telegramId` — в коде оборачивай `BigInt(ctx.from.id)`.

## Как устроен FSM клиентского бота (НЕ ломать)
FSM **ручной** (состояние — in-memory `session` grammY), но переходы **декларативны**.
Никакого плагина `conversations`, никаких scenes. Паттерн любого шага:
**проверь `step` (гард) → выполни действие → переведи `step` → погаси прошлую клаву.**

- **Переходы описаны декларативно в `client-bot.fsm.ts`:** экраны — юнион
  `ScreenIntent` (`{ kind, ...данные для рендера }`), «куда вести» решают чистые
  функции-переходы (`resolveBack`, `resolveAfterQty`, `resolveConfirm`,
  `resolveFinalizeAddress`) — без `ctx`/сервисов/async, покрыты юнит-тестами
  (`client-bot.fsm.spec.ts`). Хендлер: загрузил данные → вызвал функцию → отдал
  `ScreenIntent` в рендер. Ветвления «какой экран» в хендлерах быть НЕ должно.
- **`renderScreen` — единственное место `ScreenIntent → реальный экран`** —
  исчерпывающий `switch (intent.kind)` с `default: assertNever(intent)`. Забыл
  обработать новый экран → **компилятор краснеет** (`TS2345 … type 'never'`), а не
  падает в рантайме. Добавление экрана начинается с варианта в `ScreenIntent`.
- Состояние — `enum Step` (в `client-bot.fsm.ts`), хранится в `SessionData`:
  `AwaitContact → MainMenu → AwaitAddress → AwaitComment → ChooseQty → Confirm`.
- **Гард в каждом хендлере:** `if (ctx.session.step !== Step.X) return;`. Роутера
  состояний нет — проверки разбросаны по хендлерам, это сознательно.
- **«Назад»** — ручной стек `history: Step[]` в сессии (push на входе в шаг, pop в
  `onBack`); `resolveBack` по снятому шагу решает целевой экран.
- **Гашение клавиатур** — самое хрупкое место. Inline-экраны слать ТОЛЬКО через
  `replyInline` (гасит прошлую клаву, запоминает `activeInlineMessageId`); экраны
  с reply-меню — через `replyMenu` (гасит висящую inline-клаву). **Прямой
  `ctx.reply` для экранов сценария — запрещён**, иначе в чате остаются «мёртвые»
  кнопки. Агент, привыкший к `ctx.reply`, легко это нарушит — не нарушай.
- Диспетчерский бот — тот же подход, но проще: одно поле `editingPriceField` в сессии.

## Архитектурные правила (нарушение = баг)
1. **Расчёт суммы — только в `pricing.service.ts`.** Нигде больше суммы не считать.
2. **`OrderDispatcher` — абстракция доставки заказа.** Логика заказа не знает, куда
   уходит уведомление. Один интерфейс, разные реализации — не хардкодить бота в orders.
   Реализация выбирается в `orders.module.ts` через `resolveOrderChannel()`
   (`src/config/demo.ts`), а НЕ по голому `NODE_ENV`: демо-стенд тоже шлёт в Telegram.
3. **`totalPrice` фиксируется в Order при создании.** Не пересчитывать задним числом
   при изменении цен (см. `PRODUCT.md`).
4. **Доступ к БД — только в сервисах модулей.** Боты/хендлеры НИКОГДА не дёргают
   PrismaClient напрямую — только через сервис соответствующего модуля.
5. **Два бота — два токена, один процесс.** Логику клиента и диспетчера НЕ смешивать
   в общих хендлерах. Разделение по боту, а не if-ами по роли.
6. **Без «висящих» inline-клавиатур** (см. секцию FSM выше).
7. **Ввод из Telegram недоверенный.** `callback_data` и текст можно подделать.
   Проверяй границы чисел (кол-во ≤ `MAX_ORDER_QTY`) и владельца сущности
   (`clientId`). Не считай, что кнопку выдал твой UI.
8. **Сбой операции — всегда обратная связь.** `bot.catch` только логирует.
   Операции, способные упасть (БД, создание заказа), оборачивай в try/catch прямо
   в хендлере и показывай понятное сообщение — клиент не должен остаться в тишине.
9. **Ре-entrant шаги идемпотентны.** Если на шаг можно вернуться/попасть повторно —
   upsert/update вместо повторного create (напр. default-адрес — один на клиента).
10. **Событие, а не прямой вызов.** Смена статуса заказа уведомляет клиента через
    `order.status.changed` (event-emitter). Слушатель — fire-and-forget: любую
    ошибку (заблокированный бот, БД) гасит у себя, не роняя переход статуса.

## Тестирование
- Сейчас: **71 тест, 6 spec-файлов**, покрыт сервисный слой (pricing,
  pricing-settings, clients, orders) и чистая логика FSM ботов (client-bot.fsm,
  dispatcher-bot.fsm). Живые grammY-хендлеры тестами НЕ покрыты. e2e сконфигурён,
  но спеков нет.
- Юнит-тесты гонять `npm test`. Перед коммитом — `npm run lint && npm test`,
  не коммить на красном (CI нет, это ручная замена).
- **При добавлении логики в бот** — выноси чистую логику (переходы FSM, парсинг
  callback, валидацию) в отдельные функции и покрывай их юнит-тестами без живого
  grammY. Не тащи async-сервисы внутрь «чистых» функций — данные загружай в
  хендлере, в функцию передавай уже готовые значения.

## Локальный запуск и самопроверка
- Поднять БД: `docker compose up -d db` → `npm run db:migrate` → `npm run start:dev`.
- **Long polling, без webhook** — ngrok/туннель НЕ нужен, апдейты подтягиваются сами.
- ⚠️ **Один токен = один polling-инстанс.** Запуск с **прод**-токеном при живом
  проде даёт `409 Conflict`. Для локального прогона/самопроверки используй
  **отдельные тестовые токены** от ботов из @BotFather — НИКОГДА не прод.
- Демо-стенд локально: `cp .env.demo.example .env.demo` (свои демо-токены) →
  `npm run demo:up` → `npm run demo:logs`. Подробности и ограничения — `DEMO.md`.

(`src/config/load-env.ts`), и Prisma CLI (`prisma.config.ts`). Отсюда
`ENV_FILE=.env.demo npm run start:demo` и `npm run demo:migrate`.

⚠️ **`DEMO_MODE` меняет клиентский сценарий** (не спрашивает телефон, добавляет `/reset`,
авто-принимает заказы, открывает диспетчерский бот). Всё демо-поведение — под явным
флагом и в `src/modules/demo/`; в живой продукт эти ветки протекать не должны.

## Как добавлять фичу (в живой код)
0. Затрагивает ли фича то, что видит клиент (текст, кнопка, шаг сценария, сообщение
   об ошибке)? Сверься с `UX.md` — принципы (§1), антипаттерны (§4) и чеклист (§5).
   Обоснование и данные — в `RESEARCH-UX.md`. UX-правило нарушать нельзя так же, как
   архитектурное.
1. Сверься с `PRODUCT.md` — затрагивает ли фича существующие правила (цены,
   isFirstOrder, edge-кейсы). Если меняешь продуктовое правило — правь `PRODUCT.md`
   тем же коммитом.
2. Бизнес-логику — в сервис модуля, покрой юнит-тестами **первой** (как pricing).
3. Чистую логику бота (переходы, парсинг, валидацию) выноси в тестируемые функции.
4. Меняешь FSM — пройди ВСЕ точки шага: гард, render-хелпер (ставит step), pushHistory
   (если inline-переход внутри флоу), resetSession (если добавил поля сессии),
   `ORDER_FLOW_STEPS` (если шаг внутри сценария заказа).
5. Меняешь schema.prisma → `npm run db:migrate` + `npm run prisma:generate` → проверь
   импорты из `generated/prisma/`.
6. Перед готовностью: `npm run lint && npm test`.

## Границы — не делать без явного запроса
- Не добавлять онлайн-оплату (всегда оплата водителю).
- Не интегрировать мессенджеры водителей (диспетчер пересылает заказ вручную).
- Не назначать водителей внутри бота — это решает диспетчер.
- Не строить веб-админку — её роль выполняет диспетчерский бот.
- Не парсить старую базу адресов — адреса собираются заново через бота.
- Не расширять объём за рамки задачи. Возникла идея «а давай ещё фичу» — сначала спроси.
