# SPEC — Бот доставки воды (MVP)

> Продуктовая спецификация. Описывает **что** строим и **по каким правилам**.
> Технические конвенции и команды — в `CLAUDE.md`.

---

## 1. Назначение

Telegram-бот для приёма заказов бутилированной воды (бутыли 19 л). Цель MVP —
разгрузить телефон диспетчера: дать постоянным клиентам оформлять повторные заказы
в несколько тапов без звонка, а новым — оформить первый заказ, который диспетчер
подтверждает звонком.

Бот **не заменяет** телефон полностью — он забирает массовый простой сценарий
(повторный заказ), а редкие/сложные случаи остаются на диспетчере.

### Метрика успеха пилота
- Доля заказов, прошедших через бота (цель — хотя бы 15–20% за первый месяц).
- Снижение нагрузки на телефон в пиковые часы.
- Накопленная база структурированных адресов (побочный, но ценный результат).

## 2. Действующие лица

| Роль | Где | Что делает |
|------|-----|------------|
| **Клиент** | Клиентский бот (Telegram) | Оформляет заказ воды |
| **Диспетчер** | Диспетчерский бот (Telegram) | Принимает заказы, меняет статусы, редактирует цены, пересылает заказ водителю |
| **Водитель** | Вне системы | Получает заказ от диспетчера, доставляет, оплату берёт на месте |

> **Важно:** бот не общается с водителями напрямую. Диспетчер вручную пересылает
> готовую строку заказа из диспетчерского бота водителю (любым удобным способом).
> Распределение по водителям — целиком на диспетчере, бот в это не лезет.

## 3. Ценообразование

### 3.1 Повторный заказ (клиент уже есть в базе бота)
Цена за бутыль 19 л зависит от количества в заказе:

| Количество | Цена за бутыль | Пример суммы |
|-----------|----------------|--------------|
| 1 | 80 грн | 80 |
| 2 | 75 грн | 150 |
| 3 и больше | 70 грн | 3→210, 4→280, 5→350 … |

### 3.2 Первый заказ (клиента ещё нет в базе бота)
Вода бесплатно, оплачивается стартовый комплект:

- Залог за бутыль: **300 грн × количество**
- Помпа: **200 грн** (всегда одна в MVP)
- Вода: **0 грн**

Формула первого заказа: `количество × 300 + 200`

Примеры: 1 бутыль → 500; 2 бутыли → 800; 3 бутыли → 1100.

> **2+ помпы, чужие бутыли** — вне MVP. Если клиенту реально нужно нестандартное,
> диспетчер решит это при звонке-подтверждении первого заказа.

### 3.3 Редактирование цен
Все суммы (80/75/70, залог 300, помпа 200) **редактируются диспетчером** через
диспетчерский бот. Хранятся в БД, не в коде. Любой расчёт берёт актуальные значения
из БД на момент оформления.

## 4. Модель данных

Концептуальная схема (точная Prisma-схема — в репозитории).

### Client
| Поле | Тип | Заметки |
|------|-----|---------|
| id | uuid | PK |
| telegramId | bigint | уникальный, из Telegram |
| phone | string | из Telegram-контакта, уникальный |
| name | string? | имя из Telegram |
| createdAt | datetime | |

### Address
| Поле | Тип | Заметки |
|------|-----|---------|
| id | uuid | PK |
| clientId | uuid | FK → Client |
| raw | string | полный адрес как ввёл клиент |
| comment | string? | этаж, домофон, ориентир |
| isDefault | boolean | основной адрес |
| createdAt | datetime | |

> На старте у клиента обычно один адрес. Модель допускает несколько (дом/офис) —
> но в UI MVP показываем только default; мультиадрес — лёгкое расширение позже.

### Order
| Поле | Тип | Заметки |
|------|-----|---------|
| id | uuid | PK |
| clientId | uuid | FK → Client |
| addressId | uuid | FK → Address (снимок адреса на момент заказа) |
| bottles | int | количество бутылей |
| isFirstOrder | boolean | true → считалось по стартовой сетке |
| totalPrice | int | посчитанная сумма (грн), фиксируется на момент заказа |
| status | enum | created / accepted / delivered / cancelled |
| createdAt | datetime | |
| acceptedAt | datetime? | |
| deliveredAt | datetime? | |

### PriceSettings (одна строка-синглтон, либо key-value)
| Поле | Тип | Значение по умолчанию |
|------|-----|----------------------|
| price1 | int | 80 |
| price2 | int | 75 |
| price3plus | int | 70 |
| depositPerBottle | int | 300 |
| pumpPrice | int | 200 |
| updatedAt | datetime | |

> `totalPrice` фиксируется в заказе на момент оформления. Если диспетчер изменит
> цены позже — старые заказы не пересчитываются. Это важно для корректной истории.

## 5. Расчёт суммы (единое правило)

```
function calcTotal(bottles, isFirstOrder, prices):
    if isFirstOrder:
        return bottles * prices.depositPerBottle + prices.pumpPrice
    else:
        if bottles == 1: perBottle = prices.price1
        elif bottles == 2: perBottle = prices.price2
        else:              perBottle = prices.price3plus
        return bottles * perBottle
```

`isFirstOrder` определяется так: **у клиента (по telegramId/phone) в БД нет ни одного
заказа со статусом, отличным от cancelled** → это первый заказ.

## 6. FSM клиентского бота

Состояния диалога клиента. Бот использует **постоянную reply-клавиатуру**
с глобальной навигацией и **inline-клавиатуры** для действий внутри сценария
заказа.

**Reply-меню (всегда внизу экрана):**

- 🚰 Заказать воду
- 📋 Мои заказы
- 💰 Цены
- 📞 Связаться

**Правило глобальной навигации:** нажатие любой reply-кнопки в любой момент
отменяет текущий FSM (если он не в `MAIN_MENU`), сбрасывает локальную историю
переходов и переводит юзера на запрошенный экран. Если шёл активный заказ —
бот показывает «Заказ отменён» перед новым экраном.

Inline-кнопки «◀ Назад» / «❌ Отмена» доступны внутри сценария заказа
(`AWAIT_ADDRESS`, `CHOOSE_QTY`, `CONFIRM`):

- «Назад» возвращает на предыдущий шаг (по локальному стеку истории);
- «Отмена» сбрасывает заказ и возвращает в главное меню.

```
[START] /start
   │
   ├─ клиент не делится контактом ──► [AWAIT_CONTACT] ──(получен контакт)──┐
   │                                                                        │
   └─ контакт уже известен ─────────────────────────────────────────────► [MAIN_MENU]
                                                                            │
   [MAIN_MENU]                                                              │
   ├─ "Заказать воду" ──► определить первый/повторный                       │
   │     │                                                                  │
   │     ├─ ПЕРВЫЙ заказ:  [AWAIT_ADDRESS] ─► [AWAIT_COMMENT] ─► [CHOOSE_QTY] ─► [CONFIRM_FIRST]│
   │     │                                                                  │
   │     └─ ПОВТОРНЫЙ:     есть адрес ─► [CHOOSE_QTY] ─► [CONFIRM_REPEAT]    │
   │                       (+ кнопка "Повторить прошлый заказ")             │
   │                                                                        │
   ├─ "📋 Мои заказы" ──► [HISTORY] (последние 5 заказов, статусы)          │
   ├─ "💰 Цены" ──► [PRICES] (текущая сетка + стартовый комплект)           │
   └─ "📞 Связаться" ──► [CONTACTS] (SUPPORT_PHONE из конфига)              │

   [CONFIRM_*] ──(подтвердил)──► создать Order(status=created)
                                  ├─► уведомить диспетчера
                                  └─► [ORDER_DONE] "Заказ принят, ожидайте"
```

### Тексты ключевых экранов (черновик, можно править)

**AWAIT_CONTACT:**
> «Привет! 💧 Чтобы оформить заказ, поделитесь номером телефона — по нему мы
> определим ваш адрес доставки.» + кнопка запроса контакта.

**AWAIT_ADDRESS (первый заказ):**
> «Похоже, вы заказываете впервые 👋 Укажите адрес доставки: улица, дом, квартира.»

**AWAIT_COMMENT (первый заказ, необязательный шаг):**
> «Добавьте детали к адресу: этаж, код домофона, ориентир — или нажмите
> "Пропустить".» Кнопки: `[⏭ Пропустить] [❌ Отмена]`. Введённый текст → в
> `Address.comment`; «Пропустить» → `comment = null`. Адрес создаётся одной
> записью после этого шага.

**CONFIRM (общая структура, ветка по isFirstOrder):**
> Хочу заказать:
> 📦 {bottles} {бутыль/бутыли/бутылей} ({разбивка цены})
> 📍 {address.raw}{, comment в скобках, если задан}
> 💰 К оплате: **{total} грн** (наличными водителю)

Кнопки: `[✅ Всё верно, заказываю]` `[✏️ Изменить]` `[❌ Отмена]`
(«Изменить» = «Назад» к выбору количества).

Разбивка цены:

- повторный заказ: «по {perBottle} грн»
- первый заказ: «залог {bottles}×300 + помпа 200, вода бесплатно»

**Экраны reply-меню:**

- **HISTORY** («Мои заказы») — последние 5 заказов клиента
  (`orders.listByClient`): дата, кол-во, сумма, статус. Под заказами в статусе
  `created` — inline-кнопка `❌ Отменить #<id>`: клиент отменяет сам, пока
  диспетчер не принял (SPEC §9). После отмены список перерисовывается.
- **PRICES** («Цены») — текущая сетка из `PriceSettings` + стартовый комплект.
- **CONTACTS** («Связаться») — `SUPPORT_PHONE` из конфига (SPEC §11, заглушка).

**ORDER_DONE:**
> «Заказ принят ✅ Скоро с вами свяжутся / привезут воду. Спасибо!»

## 7. FSM диспетчерского бота

```
[НОВЫЙ ЗАКАЗ приходит автоматически]
   │
   ▼
Сообщение диспетчеру:
┌─────────────────────────────────────────┐
│ 🔔 НОВЫЙ ЗАКАЗ #1234  [ПЕРВЫЙ ЗАКАЗ ⚠️]   │
│ 2по75 Хмельницкого 2, кв.5               │
│ Клиент: Иван (+380...)                   │
│ Сумма: 150 грн                           │
│ Коммент: домофон 45                      │
│                                          │
│ [✅ Принят] [✏️ Изменить] [❌ Отменить]   │
└─────────────────────────────────────────┘
   │
   ├─ "Принят" ──► status=accepted ──► кнопки: [🚚 Доставлен] [❌ Отменить]
   │     (диспетчер вручную пересылает строку заказа водителю)
   │
   ├─ "Доставлен" ──► status=delivered ──► заказ закрыт
   │
   └─ "Отменён" ──► status=cancelled

[КОМАНДЫ ДИСПЕТЧЕРА]
/prices ──► показать текущие цены ──► [изменить цену 1] [2] [3+] [залог] [помпа]
            └─ выбрал ──► ввести новое число ──► сохранить в PriceSettings
/stats  ──► заказов сегодня/за неделю, сумма, через бота vs всего (по данным бота)
```

### Формат строки заказа для пересылки водителю
Бот формирует строку в привычном диспетчеру формате, чтобы он пересылал одним
движением. Пример: `2по75 Хмельницкого 2 кв5 (домофон 45)`.

> Точный формат подгоняется под привычку диспетчера после первого теста.
> Для первого заказа добавляется пометка, напр. `[ПЕРВЫЙ +помпа]`.

## 8. Сквозной путь заказа (happy path)

1. Клиент в боте оформляет заказ → `Order(status=created)`.
2. Бот шлёт уведомление в диспетчерский бот (с пометкой «первый заказ», если так).
3. Диспетчер жмёт «Принят» → `accepted`; пересылает строку заказа водителю.
   Клиенту автоматически уходит уведомление «Заказ принят ✅».
4. Водитель доставил и отметил выполнение.
5. Диспетчер жмёт «Доставлен» → `delivered`. Деньги взял водитель на месте.
   Клиенту уходит «Заказ доставлен 🚚».

> Смена статуса диспетчером (`accepted`/`delivered`/`cancelled`) уведомляет
> клиента в его боте через событие `order.status.changed`. Отмена самим клиентом
> (§9) клиенту повторно не дублируется.

## 9. Edge-кейсы и решения

| Случай | Решение в MVP |
|--------|---------------|
| Клиент не делится контактом | Не пускаем дальше AWAIT_CONTACT, вежливо объясняем зачем |
| Первый заказ, нужна 2-я помпа / нестандарт | Бот считает 1 помпу; диспетчер уточнит при звонке (пометка «первый») |
| Заказ из другого города / вне зоны | Бот принимает; диспетчер видит адрес и отменяет/перезванивает |
| Клиент ввёл кривой адрес | Принимаем как есть (raw); диспетчер увидит и уточнит |
| Чужие бутыли | Вне MVP — решается звонком |
| Клиент дважды нажал «подтвердить» | Идемпотентность: блокируем кнопку после первого нажатия / проверяем дубль по времени |
| Клиент отменяет заказ сам | Только в статусе `created` (диспетчер ещё не принял) и только свой заказ (проверка владельца — callback можно подделать). Диспетчеру уходит уведомление об отмене |
| Гонка: клиент жмёт «Отмена», диспетчер «Принят» одновременно | Атомарный апдейт по `where:{status:created}` — кто успел первым, тот и выиграл; второй получает «уже обработано» |
| Клиент прислал не текст на шаге адреса/комментария | Просим прислать текстом, экран не сбрасываем |
| Подделанный callback (кол-во/чужой заказ) | Кол-во ограничено сверху; владелец заказа проверяется по `clientId` |
| Сбой создания заказа (БД) | Сообщаем клиенту «не удалось, попробуйте ещё раз», не молчим |
| Диспетчер случайно отменил | Можно вернуть статус вручную (в v2 — кнопка «вернуть»); в MVP — правка в БД |
| Цена изменилась после оформления | Не пересчитываем — `totalPrice` зафиксирован в заказе |
| Бот упал/перезапустился в середине диалога | Состояние диалога в сессии; при потере — клиент начинает заказ заново (приемлемо для MVP) |

## 10. Границы MVP

### Входит
- Открытая регистрация (любой, по Telegram-контакту).
- Первый заказ (стартовая сетка) и повторный (обычная сетка).
- Сбор адреса при первом заказе, переиспользование при повторных.
- Уведомление диспетчеру + статусы (created/accepted/delivered/cancelled).
- Уведомление клиента о смене статуса его заказа диспетчером (accepted/delivered/cancelled).
- Редактирование цен диспетчером.
- История заказов клиента, базовая статистика для диспетчера.
- Постоянное reply-меню (Заказать / Мои заказы / Цены / Связаться).
- Экран «Мои заказы» — последние 5 заказов клиента со статусами; отмена своего
  заказа в статусе `created` (диспетчеру уходит уведомление).
- Экран «Цены» — показ текущей сетки и стартового комплекта.
- Экран «Связаться» — контактный телефон из конфига (`SUPPORT_PHONE`).
- Навигация «Назад» / «Отмена» внутри сценария заказа.
- Напоминание постоянным («давно не заказывали») — опционально, если успеется.

### НЕ входит (v2+)
- Автоопределение зоны доставки.
- Несколько помп, чужие бутыли, возврат залога как процесс.
- Экспорт/синхронизация с Excel или Google Sheets.
- Онлайн-оплата (всегда оплата водителю).
- Назначение водителей внутри бота.
- Веб-админка (роль админки выполняет диспетчерский бот).
