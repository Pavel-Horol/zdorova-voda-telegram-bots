# План: фичи v2 (после MVP-UX)

Четыре фичи, выбранные как «убирают звонки диспетчеру + копят данные»:

1. **Повторить прошлый заказ** (клиентский бот)
2. **Комментарий к адресу** (клиентский бот, шаг FSM)
3. **Отмена заказа клиентом** (клиентский бот + статус)
4. **Уведомление клиента о смене статуса** (кросс-ботовое — главное арх. решение)

Принцип: одна фича = один коммит, `SPEC.md` обновляется тем же коммитом
(CLAUDE.md правило 4). Расчёт цены не трогаем (только pricing.service, §1).
Схема БД: миграции не нужны нигде, кроме — возможно — фичи 3 (см. ниже).

Бэклог (не в этой итерации): `/stats` за неделю, смена адреса клиентом,
`/orders` у диспетчера, напоминания «давно не заказывали».

## Фича 1. Повторить прошлый заказ

**Цель (SPEC §6, уже значится):** постоянному клиенту — оформить тот же заказ
в один тап, без выбора количества.

### Поведение
- На экране `CHOOSE_QTY` для клиента, у которого есть **последний не-отменённый**
  заказ, над/под рядом цифр показываем кнопку `🔄 Повторить: N бутылей`.
- Тап → `bottles = N` → сразу `renderConfirm` (адрес — текущий default, как в
  обычном флоу; сумма пересчитывается заново через `quote`, т.е. по актуальным
  ценам — это корректно, фиксируется totalPrice только при создании).
- Нет прошлого заказа → кнопку не показываем (это де-факто первый заказ).

### Изменения
- **`orders.service.ts`** — read-only метод
  `lastBottles(clientId): Promise<number | null>` (последний заказ со статусом
  ≠ CANCELLED, вернуть `bottles` или null). Доступ к БД — внутри сервиса (§6).
- **`client-bot.service.ts`** — в `renderChooseQty` подгрузить `lastBottles`,
  при наличии добавить в `qtyKeyboard` кнопку `qty:N` (переиспользуем тот же
  callback — он уже ведёт в `onChooseQty`). Динамическая клавиатура → собирать
  её в методе, а не константой.
- **`client-bot.texts.ts`** — подпись кнопки повтора (со склонением).
- **`SPEC.md` §6** — отметить как реализованное.

### Риски
- `qtyKeyboard` сейчас константа; станет функцией `qtyKeyboard(repeatN?)`. Мелочь.
- Дёшево, изолировано. Делаем первой.

## Фича 2. Комментарий к адресу

**Цель:** при первом заказе собрать этаж/домофон/ориентир в `Address.comment`
(поле уже есть, бот его сейчас не заполняет). Улучшает данные для водителя.

### Поведение
- Новый шаг `AWAIT_COMMENT` после `AWAIT_ADDRESS` (только первый заказ).
- Текст: «Добавьте этаж, код домофона, ориентир — или нажмите Пропустить».
- Inline-кнопки: `[⏭ Пропустить] [❌ Отмена]`. Текст → сохраняем как `comment`;
  «Пропустить» → `comment = null`. Затем → `renderChooseQty`.

### Изменения
- **`client-bot.service.ts`**
  - Сейчас адрес создаётся прямо в `onText`/`AwaitAddress`. Меняем: `raw`
    кладём в сессию (`session.addressRaw`), идём в `AWAIT_COMMENT`, и только
    после комментария/пропуска вызываем `clients.addAddress({raw, comment, isDefault:true})`.
  - Новый шаг в enum `Step`, новый callback `CB_SKIP`, новое поле сессии
    `addressRaw?`. Шаг включить в `ORDER_FLOW_STEPS` и в стек истории.
  - `renderCommentPrompt(ctx)` хелпер.
- **`client-bot.texts.ts`** — `awaitComment`.
- **`SPEC.md` §6** — добавить шаг в FSM первого заказа.

### Риски
- Трогает порядок создания адреса и стек «Назад» — аккуратно с историей.
- Средне-дёшево. Делаем второй.

## Фича 3. Отмена заказа клиентом

**Цель:** клиент отменяет свой заказ сам, пока диспетчер не принял (= меньше
звонков «отмените»).

### Поведение
- В «Мои заказы»: у заказов в статусе `CREATED` — inline-кнопка
  `❌ Отменить #xxxx`. Для `ACCEPTED`+ кнопки нет (уже в работе → звонок).
- Тап → проверяем, что заказ принадлежит этому клиенту **и** статус `CREATED`,
  переводим в `CANCELLED`, перерисовываем список.

### Изменения
- **`orders.service.ts`** — `cancelOwnOrder(orderId, clientId)`:
  загрузить заказ, проверить `clientId` совпадает и `status === CREATED`,
  иначе бросить/вернуть отказ. (Не переиспользуем `cancelOrder` — у него нет
  проверки владельца и он разрешает ACCEPTED.)
- **`client-bot.service.ts`** — рендер истории с кнопками `cancel:<id>`,
  обработчик `onCancelOwnOrder`.
- **`SPEC.md` §6/§9** — правило: клиент может отменить только `CREATED`.

### Уведомление диспетчера — РЕШЕНО: вариант B
- При отмене клиентом шлём диспетчеру пуш «Клиент отменил заказ #xxxx».
  Расширяем `OrderDispatcher` методом `notifyClientCancelled(order, client)`
  (+ реализация в `TelegramOrderDispatcher` и `LogOrderDispatcher`).
- `cancelOwnOrder` после успешной отмены зовёт `dispatcher.notifyClientCancelled`.

### Риски
- Безопасность: callback с чужим `orderId` — проверка владельца обязательна.
- Отправка диспетчеру может упасть (чат/токен) — ловить и логировать, не валить
  саму отмену.
- Делаем третьей.

## Фича 4. Уведомление клиента о смене статуса  ⚠ арх. решение

**Цель:** диспетчер жмёт «Принят»/«Доставлен»/«Отменён» → клиенту прилетает
«Заказ принят ✅ / Везём 🚚 / Отменён». Убирает звонки «где мой заказ».

### Главный вопрос: КТО шлёт клиенту?
Смену статуса делает `OrdersService` (acceptOrder/markDelivered/cancelOrder) —
единая точка. Но отправка идёт через **клиентский** Bot-инстанс, который живёт
в `ClientBotService`. Нужен способ из orders достучаться до клиентского бота.

**Вариант A — зеркало `OrderDispatcher` (консистентно с тем, что есть).**
Ввести `ClientNotifier` (интерфейс в `bots/shared`) с методом
`notifyStatusChange(order, client)`. Реализация `TelegramClientNotifier`
использует клиентский Bot. `OrdersService` инжектит `ClientNotifier` и вызывает
после успешного перехода.
- Плюс: один в один как `OrderDispatcher`, никаких новых зависимостей, явный поток.
- Минус: клиентский бот сейчас создаёт `Bot` **внутри** `onModuleInit` (не через
  провайдер). Нужно вынести инстанс в shared-провайдер + core-модуль (как у
  диспетчера: `dispatcher-bot.bot.ts` + `DispatcherBotCoreModule`). Рефактор
  клиентского бота на общий инстанс.

**Вариант B — события NestJS (`@nestjs/event-emitter`).**
`OrdersService` эмитит `order.status.changed`; `ClientBotService` слушает
`@OnEvent` и шлёт через свой Bot.
- Плюс: без рефактора клиентского бота, без кросс-модульного шаринга инстанса.
- Минус: новая зависимость + «магия» событий (поток менее явный, чем DI).

**Рекомендация:** **Вариант A** — он повторяет уже существующий паттерн
`OrderDispatcher`, не плодит новых концепций и держит поток явным. Рефактор
клиентского бота на shared-инстанс небольшой и заодно выравнивает оба бота под
один стиль. (Если хочешь минимум диффа — берём B.)

### Изменения (для варианта A)
- **`bots/client-bot/client-bot.bot.ts`** (новый) — провайдер `CLIENT_BOT`
  + `ClientBotCoreModule` (по образцу диспетчера).
- **`client-bot.service.ts`** — берёт инстанс из `CLIENT_BOT` (DI), не создаёт сам.
- **`bots/shared/client-notifier.ts`** (новый) — интерфейс `ClientNotifier`
  + `LogClientNotifier` (dev) + токен.
- **`bots/client-bot/telegram-client-notifier.ts`** (новый) — прод-реализация.
- **`orders.module.ts`** — провайдер `CLIENT_NOTIFIER` (env-switch как у dispatcher),
  импорт `ClientBotCoreModule`.
- **`orders.service.ts`** — после accept/deliver/cancel звать `clientNotifier`.
  Нужен `client` — догрузить по заказу (или вернуть из transition).
- **`client-bot.texts.ts`** — тексты статусов для клиента.
- **`SPEC.md` §7/§8** — отметить, что клиент получает уведомления.

### Риски
- Клиент мог удалить чат/заблокировать бота → отправка кинет ошибку: ловить и
  логировать, не валить транзакцию заказа.
- Самая «тяжёлая» фича. Делаем последней, после согласования варианта A/B.

## Рекомендуемый порядок

1. **Повторить заказ** — дёшево, ядро ценности, изолировано.
2. **Комментарий к адресу** — изолированный шаг FSM.
3. **Отмена клиентом** (вариант B: с пушем диспетчеру `notifyClientCancelled`).
4. **Уведомление клиента о статусе** — ОТЛОЖЕНО: решение A (ClientNotifier) vs
   B (события NestJS) примем, когда дойдём до неё.

Каждый пункт: код + `SPEC.md` + (где дёшево) юнит-тест на новый метод сервиса.
